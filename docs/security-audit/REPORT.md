## 2. Posture summary

The core authorization model is sound. Every tRPC data query is owner-scoped by the session `userId`. `adminProcedure` re-reads the role from D1. Stripe webhooks verify signatures. User-controlled text is HTML-escaped before it reaches invoice and email templates. No route in the source gives one user another user's data.

The risk is concentrated in four themes, all needing runtime or deployment facts to settle:

1. **Better Auth hardening on Workers.** The rate limiter's enablement depends on an unset `NODE_ENV`. The KV `increment` can drop TTLs. The captcha list names a nonexistent route. Sessions survive password reset and account deletion in KV. The auth secret falls back to a default when it is unset.
2. **Stripe webhook state integrity.** The event id is committed before side effects run, so a failed delivery is never retried. Subscription lifecycle handlers key on metadata that checkout never sets.
3. **Non-atomic money and fiscal flows.** Referral rewards and NFSe re-emission use check-then-insert without a unique constraint or transaction.
4. **Environment fail-open defaults.** An unset `ENVIRONMENT` is treated as development, which exposes tRPC stack traces. Staging seeds carry documented known passwords.

## 6. Hardening notes and positive patterns

### Hardening (not findings; no boundary result was established)

- wrangler.jsonc top level binds unused staging resources (D1 cf_boilerplate_staging, R2 cf_boilerplate_storage_staging) and duplicate production aliases (cf_boilerplate_db, cf_boilerplate_storage) into the production worker. Remove them so a future code path or compromised dependency in production cannot reach staging data.
- deploy-production.yml has no permissions: block. Add 'permissions: contents: read'.
- deploy-production.yml has no needs: or required-checks gate on CI. A push to main deploys and migrates production even if tests fail. Add a workflow_run dependency, or enforce branch protection and environment reviewers for the 'production' environment (not verifiable in source).
- Actions are tag-pinned (@v4, @v2, @v3) and bun-version is 'latest'. Pin actions to commit SHAs and bun to an exact version. The migration step runs wrangler from node_modules with the production CLOUDFLARE_API_TOKEN, so a compromised dependency on main would receive that token. Use a scoped token (D1 edit plus Workers deploy only).
- The migration step could pass the token only to the wrangler invocation. The type-check and build steps run before the token is exposed, which is good. Keep that order.
- createAppConfig treats unset ENVIRONMENT as development (fail-open). Fail closed instead: treat only an explicit 'development' as development, and throw on unknown or missing values in deployed workers. Unify the ENVIRONMENT checks in index.ts and corsMiddleware.ts through createAppConfig instead of the mixed ===, !== and includes comparisons.
- The 'Upload Sentry source maps' step is dead code. env.SENTRY_AUTH_TOKEN is undefined at job level, and no sentry:sourcemaps script exists in package.json. Fix or remove it.
- package.json cf:deploy:production uses --env production, but wrangler.jsonc has no env.production block. Remove the flag or add the block, to avoid ambiguity about which config deploys.
- vite.config.ts emits public source maps for staging and production builds (sourcemap: environment !== 'local'). They are served from ASSETS. This is low-risk exposure of client source only. Consider hidden sourcemaps and upload them to Sentry only.
- Replace env.BETTER_AUTH_SECRET ?? "" with an explicit throw when the secret is missing or shorter than 32 characters.
- Pass isDev: false (or derive it from env.ENVIRONMENT) to initTRPC.create().
- Make isDevelopment require ENVIRONMENT === 'development' explicitly instead of treating an unset value as development.
- Wrap readCookie in the user-create hook in try/catch, since decodeURIComponent can throw URIError on a malformed % sequence.
- Escape single quotes in services/emails/html-utils.ts escapeHtml.
- Trim entries when splitting trustedOrigins in auth.ts.
- Cover the emailOTP endpoints with Turnstile in addition to the four currently covered endpoints.
- Add length limits to nfse.updateSettings and invoices.create string inputs.
- Restrict /api/v1/health so it does not expose ENVIRONMENT.
- Add a host allow-list and size cap for pdfUrl/xmlUrl fetches in the NFSe workflow (h06).
- Make KV secondaryStorage getAndDelete and increment atomic, or document the race, for the OTP and rate-limit paths.
- Remove the top-level cf_boilerplate_* staging D1/R2 bindings from the production wrangler config (h09).
- src/server/lib/auth.ts builds trustedOrigins with TRUSTED_ORIGINS.split(',') and does not trim or filter. The CORS middleware does trim and filter. A value with spaces after the commas fails closed in Better Auth but could break legitimate origins, so apply the same trim and filter.
- The record.pdfUrl and record.xmlUrl values from the Fiscal API are rendered as href in invoices/$id.tsx with no scheme check. React 19 blocks javascript: URLs, so this is not exploitable today. Validate that they are https on the server (the NFSe workflow, owned by h06) for defense in depth.
- The CORS middleware returns allowedOrigins[0] for unknown origins instead of omitting the ACAO header. This is not exploitable because the browser rejects the mismatch, but returning no ACAO header would be cleaner. Add 'Vary: Origin' for cache correctness.
- src/client/routes/(protected)/dashboard/invoices/index.tsx:357 and :502 link to /api/invoices/... while the REST router is mounted at /api/v1. Check that these paths resolve. This is a functional concern and not a security finding.
- invoices.create (src/server/routers/trpc/invoices.ts) accepts unbounded items and string lengths and has no per-user invoice quota. generateInvoiceNumber runs a year-wide COUNT per create. Cap items (for example 100), cap string lengths, and add a per-user invoice quota to protect D1 storage.
- Invoice numbers are computed from a global count with only 5 retries (src/server/services/invoices.ts), so concurrent creates can fail with an error under contention. This is a correctness and availability concern that h05/h04 may own.
- tRPC has no explicit body-size or per-user rate limit outside Better Auth. Consider a per-user limiter on mutating procedures, especially invoices.resendEmail and other email-sending procedures.
- Better Auth's rate limiter is read-then-write on KV (non-atomic). Concurrent bursts can under-count, and KV allows about 1 write/s per key. Consider a Durable Object or the Workers Rate Limiting binding.
- Host gating uses host.includes('api.'). The staging API host 'api-staging.yourdomain.com' does not contain 'api.', so the /api/auth gate and the JSON root do not apply there. Compare the exact configured API hostnames instead. No cross-principal impact, since both hosts hit the same Worker.
- readCookie calls decodeURIComponent outside the try block in the user-create hook (src/server/lib/auth.ts:129, src/server/lib/cookies.ts:15). A malformed referral_code cookie yields a 500 after the user row is created. Wrap it in the try block.
- BETTER_AUTH_SECRET falls back to '' and unset ENVIRONMENT is treated as development (OTP and reset links are logged and emails are skipped). Owned by h10, noted for context.
- The sessionCache cookieCache (300s) keeps revoked sessions usable for up to 5 minutes, a documented library trade-off. Consider disableCookieCache for sensitive routes.
- TRUSTED_ORIGINS is split without trim, so a space after a comma yields an unmatched origin (it fails closed).
- Google and GitHub providers are registered with empty-string client credentials when env is unset. Register them only when configured.
- emailOTP storeOTP defaults to plain. Set 'hashed' to limit exposure if KV is read.
- The cron cleanup of D1 verification and session rows is largely moot, since both are stored in KV with TTL (no storeInDatabase or storeSessionInDatabase).
- Pin `rateLimit.enabled: true` (or derive it from config.isProduction) and set `advanced.ipAddress.ipAddressHeaders: ["cf-connecting-ip"]` so the key scope is Cloudflare's trusted client IP.
- Add a per-recipient (email hash) send budget for OTP, reset and verification emails, independent of IP.
- Use the library default captcha endpoint set plus /send-verification-email and the /email-otp/* send routes, or disable the emailOTP routes that the UI does not use; fix the client to call requestPasswordReset (/request-password-reset) with the x-captcha-response header.
- Trim the TRUSTED_ORIGINS split and handle cookie decode errors in readCookie (out of scope here).
- services/invoices.ts generateInvoiceNumber counts invoices across ALL users, so invoice numbers are global and sequential. This leaks the platform-wide invoice volume to any user, and two users can see adjacent numbers. The unique index plus retry prevents collisions, but the numbering is not per-tenant.
- emails/html-utils.ts escapeHtml omits the single quote. This is safe today because all uses are inside double-quoted attributes or text nodes, but it is fragile if a single-quoted attribute is added.
- emails/invoice.ts double-escapes invoiceNumber for the title, because wrapEmailBody escapes the title again. It is cosmetic only and safe.
- invoices.cancel has no status guard, so a user can cancel their own paid or Stripe-synced invoice. That is a business-logic concern for the peer billing unit.
- resendEmail ignores the sendEmail result and always returns queued:true, even when the send is skipped or fails.
- download and downloadPdf throw plain Error ('Invoice not found'), not TRPCError NOT_FOUND. The behaviour is the same for non-owners and missing rows, so there is no oracle.
- createCheckoutSession does not reject a user who already has an active subscription (src/server/routers/trpc/billing.ts). A second checkout re-grants credits and overwrites stripeSubscriptionId, orphaning the first Stripe subscription, which keeps billing and keeps granting cycle credits through the customer-id lookup. This is mostly owned by h04-billing.
- The 'starter' / 200-credit fallback for an unknown price id in checkout.session.completed (webhooks.ts lines 105 and 124) should fail closed or log, to protect against env/Stripe price drift.
- Credit grants have no idempotency key tied to the Stripe invoice or payment intent. A unique index on (type, stripe reference) in credit_transactions would add defense in depth against replays.
- invoice.payment_succeeded is skipped without logging if no subscriptions row matches the customer id. The event is recorded and never retried.
- The event handlers do no ordering check (event.created or subscription state version) before overwriting state. This is low risk while the lifecycle handlers are no-ops, but it becomes relevant once they are fixed.
- I did not check whether an unset STRIPE_WEBHOOK_SECRET is rejected explicitly before constructEventAsync.
- createAppConfig (src/server/lib/config.ts) was not inspected, and the mode='payment' (credit package) purchase path has no webhook handler (only subscription mode is handled), so credit_packages cannot be fulfilled via this webhook.
- api-keys: verifyApiKey is dead code and the api_keys table has no scope, revokedAt, paused or expiry column. A future consumer must look up by keyPrefix or hash, bind the key to userId, and add scopes. The assignment mentions 'pause state' but none exists in the schema.
- admin.updateUserRole: the last-admin check is a non-atomic read-then-write. Concurrent demotions by two admins could leave zero admins. Use a single conditional UPDATE or a D1 batch.
- admin.updateUserRole does not revoke the demoted or promoted user's sessions. The admin check re-reads the DB role, so this is safe for tRPC.
- admin.getActivity and listUsers expose the PII (email, session IP) of all users to admins by design. This is acceptable under the operator-only policy.
- invoices.downloadPdf/resendEmail/nfse reEmit/nfse.cancel throw plain Error for not-found, which gives INTERNAL_SERVER_ERROR. This is not a security issue but should be a TRPCError NOT_FOUND. invoices.cancel allows cancelling an invoice in any status, including paid, and invoices.create accepts unbounded strings and arrays. Those are business-logic and resource limits owned by h05/h06.
- invoices.generateInvoiceNumber counts invoices globally rather than per user. Numbers leak only a global count. Consider per-user sequences if the global total is treated as confidential.
- billing.createCheckoutSession does not check for an existing active subscription. A second checkout overwrites stripeSubscriptionId, so the first Stripe subscription keeps billing and cannot be cancelled from the app. Reuse the portal flow, or reject checkout when status is active.
- Plan credits are granted on checkout.session.completed without checking session.payment_status, and allow_promotion_codes is true. Referral rewards qualify on a 100%-off or unpaid checkout. Gate both grants and the referral reward on payment_status === 'paid' or on invoice.payment_succeeded.
- The referral paymentIdentity is the lowercased billing email with no plus-address or Gmail-dot normalisation. A sybil referrer and referred pair still needs one paid checkout per reward, but identity-based dedupe can be bypassed with alias addresses. Consider also deduping on the Stripe customer fingerprint or card fingerprint.
- The monthly referral cap is a non-atomic count-then-insert, so concurrent webhooks could exceed it slightly. Make the cap check and the reward insert one guarded statement.
- A referral rejected for 'monthly_cap' is marked 'rejected' permanently and is never retried in a later month.
- A released referral slug can be claimed by another user, who then receives attribution from old links and cookies still in circulation. Reserve retired slugs, or key attribution to an immutable code id. Brand-like slugs such as 'official' and 'stripe' are not in the reserved list.
- getPortalUrl and cancelSubscription throw plain Error, which returns INTERNAL_SERVER_ERROR instead of a typed TRPCError. Use NOT_FOUND or PRECONDITION_FAILED.
- addCredits computes balanceAfter from a stale pre-update read, so ledger rows can be inexact under concurrency. Use UPDATE ... RETURNING as deductCredits does.
- Credits are not revoked when a subscription is deleted, refunded or charged back. Decide whether that is intended.
- nfse.cancel has no state guard. It does not require status === 'issued', so it can be called on error, processing or already-cancelled records and can race an in-flight workflow poll, which later marks a cancelled record as 'error'. Add a status check and a conditional UPDATE.
- Workflow storeFilesAndNotify fetches pdfUrl and xmlUrl with no host allow-list (https and the Fiscal API domain), no size cap and no redirect policy. The provider is trusted, so this is hardening only. Check content-length and cap the buffered size before writing to R2.
- Zero-decimal currencies (jpy, krw, clp) are in BACEN_CURRENCY_CODES, but the workflow divides foreignCurrencyAmount by 100 unconditionally. The Stripe tier returns charge.amount in whole units for these currencies, so the foreign amount on the fiscal document is understated 100x.
- formatDateForPtax uses local runtime date and timezone. This is minor but unspecified for BCB date semantics.
- reEmit throws plain Error('Invoice not found') rather than TRPCError NOT_FOUND. This gives an INTERNAL_SERVER_ERROR and is not a security issue.
- Add rate-limiting or an attempt cap on reEmit and cancel cycles (attemptCount exists in the schema but is unused). Each cycle can create a real fiscal document, which is operator-owned spend.
- Fix for the candidate: in deleteAccount, call the Better Auth path that purges secondary storage (auth.api.deleteUser with the password, or ctx.internalAdapter.deleteUser / auth.api.revokeSessions before the DB delete). Alternatively, enumerate active-sessions-{userId} in SESSION_KV and delete the tokens. As defence in depth, have protectedProcedure or sessionMiddleware verify the user row still exists, or enable session.storeSessionInDatabase.
- R2 objects (invoices/{id}/invoice.html and NFSe PDF/XML) are not deleted on account deletion. They are unreachable through the app because access is DB-row-gated, but they are a retention and privacy leftover. Delete the R2 prefixes before the user delete, or add a cron sweep for orphans.
- In-flight NFSe workflow or queued email work for a deleted user is not cancelled. Writes would fail the FK or orphan R2 objects. Consider cancelling workflow instances in deleteAccount.
- The Stripe cancel is done before the DB delete, which is the correct order. Add idempotency handling for a retry after a partial failure (subscription already cancelled), because cancelSubscription errors on an already-cancelled sub would block the delete.

### Positive patterns observed

- Every user-owned tRPC query predicates on the session `userId`, so no cross-tenant read or write path was found.
- `adminProcedure` re-reads `user.role` from D1 instead of trusting the session cache.
- The Stripe webhook verifies its signature (`constructEventAsync`) before reading the event, and dedupes on the event id.
- `escapeHtml` is applied to user-controlled text in invoice and email HTML. The client uses no `dangerouslySetInnerHTML`.
- `user.deleteAccount` requires the password or a fresh session (under 15 minutes).
- API keys are stored hashed and verified in constant time.
